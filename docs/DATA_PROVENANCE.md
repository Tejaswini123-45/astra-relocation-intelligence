# Data provenance

Every dataset, layer and constant in ASTRA carries one of four provenance classes,
enforced as a Pydantic enum and shown next to the value wherever it is displayed.

| Class | Meaning |
|---|---|
| `REAL_OPEN` | A real public dataset, used as published |
| `DERIVED` | Computed by ASTRA from `REAL_OPEN` inputs (slope, HAND, drainage density, kernel density, hazard surfaces) |
| `SYNTHETIC_CALIBRATED` | Generated by ASTRA, calibrated to the real study area, and clearly fictional |
| `DEMO_CONFIG` | A threshold, weight or policy constant chosen by ASTRA - not a government rule |

The live registry is served at `GET /provenance` and rendered on the Study Area
& Data and Model & Provenance screens. Each record carries source, source URL,
class, acquisition date, processing, resolution, temporal coverage, confidence
and licence.

## The synthetic layer, and why

Terrain, rivers, roads, elevation, land cover, rainfall and historical incidents
are real. **The twelve habitations and six candidate relocation sites are
synthetic**, placed at terrain-plausible locations with fictional names
(`Devgarh Tok`, `Naulkhet`, ...) and IDs `H-01`-`H-12` and `S-01`-`S-06`.
Demographic proportions are calibrated to district-level figures; the absolute
counts are generated.

This is deliberate. ASTRA never renders an analytical red-zone classification
over a real named village with real population figures. Every screen that shows
habitations carries the notice:

> Demonstration scenario. Habitation and site records are synthetic and
> terrain-calibrated. Not an official hazard designation of any real settlement.

## Constants

Every weight, threshold and norm lives in `apps/api/astra/domain/model_config.py`
and is served at `GET /model/config`. A constant is either `DEMO_CONFIG` and shown
with that chip, or standard-derived and carries its citation (Sphere Handbook
water, sanitation and site-area norms; PMAY-G; NDMA). A test refuses to construct
a non-`DEMO_CONFIG` constant without a citation.

## Offline guarantee

Every real dataset is fetched once by `scripts/ingest.py` and vendored under
`data/raw`. The API reads only local files; the frontend talks only to the API.
The demonstration runs with the network unplugged and no LLM key.

## Integrity gate

`scripts/validate_fixtures.py` runs in CI and on API startup and fails hard on
duplicate IDs, dangling references, coordinates outside the study bounding box,
negative or non-finite values, missing provenance, or missing required fields.
The API refuses to start on invalid fixtures.
